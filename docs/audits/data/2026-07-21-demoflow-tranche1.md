### F4 — [MED / spec-gap]

**Claim.** `extracted_at` carries TWO different semantics under one field name across the twelve envelope entries. For the eight ACQUIRED sources it is the date the bytes were pulled from upstream — correct spec §7 semantics. For the four DERIVED rate artifacts it is the UPSTREAM source's pull date, read out of the artifact's own `_provenance`, while the `sha256` beside it is the digest of the DERIVED bytes. So the pair describes two different objects, and the published date understates the labelled object's age by up to 28 days.

**Evidence.** MEASURED against the committed golden. demoflow/artifacts/rankings.json publishes headship_by_age.json {extracted_at: 2026-07-21, sha256: d33059c3…}; `git log -1 --date=short -- demoflow/data/headship_by_age.json` = 2026-08-18 — a 28-day gap between the date published and the object digested. Same shape at ownership_by_geo_age.json (published 2026-07-21, file committed 2026-08-14) and ownership_hors_aligned.json (published 2026-08-15, committed 2026-08-18). Producer: demoflow/src/demoflow/pipeline.py:330 pairs `hashlib.sha256(raw).hexdigest()` (the derived bytes) with `_artifact_extracted_at(name, raw)` (pipeline.py:281, the artifact's `_provenance.extracted_at`, which every generator writes as its UPSTREAM pull date — verified by dumping all four `_provenance` blocks). Spec §7 defines the entry as `{<source>: sha256-of-raw-response, extracted_at}` — one object, one date; it never contemplates a DERIVED artifact as a source (run 30 admitted the four into SOURCE_KEY_REGISTRY, artifacts.py:157-161, on an attribution argument that says nothing about the date). NOT covered by the ledger: run 31's record verified only that the values are per-source, non-wall-clock, stable and distinct ('2026-07-21 / 2026-08-08 / 2026-08-15'), never that the pairing is semantically honest. The failure mode is exactly the one loaders/vintage.py's own docstring records as a MEASURED defect one module over ('one map, two silently different semantics, under a single field name').

**Fix.** Rule which object the pair describes and make every entry state the same thing. Cheapest honest option: keep the derived artifacts' digests (they are the attribution that matters) and have each `scripts/gen_*.py` write a SECOND `_provenance` field — `derived_at`, the generation instant — with `_artifact_extracted_at` reading THAT for the four RUN_ARTIFACTS entries, so the date and the digest describe one object. The upstream pull dates are not lost: they already ride the envelope on their own ACQUIRED-source rows (census_tenure_age_98100231.csv, living_arrangement_98100134.json, hors_aligned_csd_98100232.json, pop-as-qc-base.xlsx). Pin it with a test asserting, for each of the four, that the envelope's extracted_at is not EARLIER than the extracted_at of every source named in that artifact's `_provenance.sources` — today headship_by_age.json fails that inequality's spirit by construction. Secondary hygiene, same file: pipeline.py:143 `_ISQ_PULL` is one literal serving two semantically independent dates (the five ISQ workbooks' pull AND the census extract's, which coincide only by accident of calendar) — split them so a future ISQ re-pull cannot silently move the census extract's declared extraction date.
