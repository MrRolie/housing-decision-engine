### F3 — [MED / code-defect]

**Claim.** The IRCC suppression envelope is centred where the arithmetic is not. `RealizedLandings.envelope` returns a SYMMETRIC ±2.5·n_cells and its docstring calls it "±(rounding + suppression)", but suppression is ONE-SIDED: a `--` cell contributes 0 to `value` and its true contribution lies in [0, +5]. The rounding leg (±2.5 per NUMERIC cell) is correct; the suppression leg is not — it should be a centre SHIFT of +2.5·n_suppressed with a ±2.5·n_suppressed half-width, i.e. [value, value + 5·n_s]. The strongest statement is internal: the same module already models the suppressed cell correctly one-sided one constant away, at the degenerate floor `SUPPRESSED_CELL_MAX * realized.n_suppressed` — the envelope contradicts its own neighbour.

**Evidence.** `output/tripwires.py:402-405` `def envelope(self): return CELL_ROUNDING_HALFWIDTH * self.n_cells` (2.5 × ALL cells, suppressed included), against `output/tripwires.py:373` `SUPPRESSED_CELL_MAX = 5.0` used one-sided at line 585 `floor = SUPPRESSED_CELL_MAX * realized.n_suppressed`. REPRODUCED on the committed frozen slice `demoflow/tests/fixtures/ircc_pr_qc_slice.csv` (Quebec province rows): 2025 — 355 cells, 304 numeric, 51 suppressed, value 60,010; the code publishes ±887.5 => [59,122.5, 60,897.5], the honest interval is [59,250.0, 61,025.0] — shifted DOWN by 2.5×51 = 127.5, with the upper bound understating the arithmetic maximum by 127.5. 2026 — 174/142/32, value 21,720, shift 80.0. Exactly the dispatch's figure: 51 cells whose true contribution lies in [0, +255]. Reach: `envelope` appears only in the run-log string at `tripwires.py:692`, never in the OK/CROSSED verdict, and the indicator is structurally UNKNOWN on the committed tree — so this is latent, not live. SECONDARY, and it does NOT refute ruling U's presence-bar inference: the tree carries two disagreeing statements about the token's own domain — `loaders/ircc.py:31` "a suppressed cell is the literal token `--` (values 0-5, per the live package notes)" vs spec ruling U / `tripwires.py:357` "the feed publishes `--` for 1-5 and omits true zeros". Under the 1-5 reading the code's lower bound sits 51 landings below what is even possible.

**Fix.** Publish the interval rather than a symmetric half-width: `[value - 2.5*n_numeric, value + 2.5*n_numeric + SUPPRESSED_CELL_MAX*n_suppressed]`, or keep a half-width and state the centre as `value + 2.5*n_suppressed`. Either way the docstring must stop claiming one number covers both legs. Separately, reconcile the 0-5 vs 1-5 statement in one commit — the two live in modules that already import each other.
