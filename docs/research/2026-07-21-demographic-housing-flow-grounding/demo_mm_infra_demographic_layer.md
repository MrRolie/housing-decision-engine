**(1) What the demographic-confidence layer actually computes, and from what.**

The layer's design (archived spec: `mm-infra/docs/superpowers/specs/archive/2026-05/2026-05-22-demographic-confidence-layer-design.md`) is a US+Canada equity-fear-premium projection over 2026-2050, built as three chained layers: Layer 1 deterministic cohort cash-flow projection (`Net_equity_flow(y) = Contribution − Distribution + Transfer`, driven by working/retired population by age, median wage, savings rate, equity allocation, and death-driven wealth transfer with a heir-redeployment fraction); Layer 2 a behavioral overlay translating equity flows into structural VRP-demand (advisor hedge-fraction × options-adoption); Layer 3 an AI/electricity regime modulator (three states, multiplier on expected VRP return). Data sources: US Census population projections, BLS CPS wages, Fed SCF wealth microdata, ICI Factbook savings/allocation, SOA Pri-2012 mortality tables, Cerulli/CRR wealth-transfer estimates, IRS SOI estate data, StatsCan equivalents. Output feeds a doctrine table (VRP capital allocation zones, trade-structure aggression by tier, the 13-15yr compound-window envelope in SINGULARITY.md) and a 6-scenario stress matrix (E[lifetime] = 13.44yr point estimate).

**Critical status caveat: the projection code is DEAD.** `research/2026-05-22_demographic_flow_model.ipynb` and its supporting `demographic_flow_model.py` (containing `layer1_cash_flow_projection`, `layer1_sensitivity_sweep`, `layer2_behavioral_overlay`, `layer3_ai_regime_modulator`, `compute_expected_lifetime`, and the loaders `load_us_population_projections`, `load_scf_wealth`, `load_bls_wages`, `load_ici_401k`, `load_mortality`, `load_statcan_cube`) were deleted from HEAD at commit `c47f14d5` ("chore(deadcode)", 2026-06-27). They survive only in a stale `.pyc` and in the `.claude/worktrees/genesis-execute-wiring/research/` copy. The spec itself was moved to `docs/superpowers/specs/archive/2026-05/`. `SINGULARITY.md` still cites both paths as "load-bearing math," which the 2026-07-18 Y1 verification memo flags as a documentation-integrity defect (points at archived/deleted artifacts).

**A fresher, load-bearing correction (2026-07-18 Y1 memo, `docs/thesis/analysis/2026-07-18-y1-demographic-flow-verification.md`):** an operator-commissioned verification concluded the demographic wealth-transfer flow yields **NO $/yr driver** for the fund. The headline "$70-90T of equity" is a 2-3x overstatement (it's total wealth, not equity; corrected net equity flow ≈ $0.5-1.0T/yr, market-wide, no fund-capturable slice). More importantly, a passive-default transfer dollar lands ~10x more heavily on the fund's Tier-2 megacap head (~18.5% S&P weight) than on Tier-1 electrification mid-caps (~1.7-1.9%) — the demographic flow does NOT differentially support the fund's Tier-1-over-Tier-2 thesis axis. Verdict: the layer is a **thesis-validity signal only, explicitly ruled "not a revenue term in the money packet."** The layer was never a $/yr-generating model even in its designed form — it's a doctrine/sizing informant, not a strategy.

**(2) What the tripwires monitor, and cadence.**

`mm-ops-demographic-tripwires` (systemd, lain-node) is scheduled monthly (5th, 04:00 America/Toronto) but **the timer is not installed** — first scheduled run would be ~Aug 5, per the scheduled-agents inventory. Of the 7 designed tripwires (in `ops/lain/demographic-tripwires/thresholds.yaml`), only 2 are actually wired: CBOE VIX 6-month rolling mean (<12 sustained) and Tier-1 IV/RV spread compression, both via the canonical `market_features` ArcticDB library across the 21-name Tier-1 universe. The other 5 (US/CA DC net equity flow, real wage growth, net immigration cut, ICI 401k allocation drop, Tier-1 forward P/E percentile) ship as `NotImplementedError` stubs and surface as `stub:` rows in the brief — wiring is deferred, not built. There's a known structural gap (#680): the wired IV/RV check compares a spread LEVEL against a `6mo_change` threshold, so it structurally can't fire on compression as designed. Output: brief to `$MM_BRIEF_DIR/proposals/` only when fired/near (skip-on-clean), Telegram only on FIRED. Bottom line: the tripwire monitor is a live but largely-skeletal scaffold, not a functioning 7-signal system.

**(3) Machinery reusable for a Québec housing cohort-flow model.**

Nothing is reusable by import — `packages/` is repo-doctrine forbidden from importing `research/`, and the code in question is deleted from HEAD anyway. What's reusable is the **pattern**, resurrectable via `git show c47f14d5^:mm-infra/research/demographic_flow_model.py` or copied from the surviving worktree copy: the age-cohort population-projection loaders (`load_us_population_projections`, `load_statcan_cube`, `melt_population_wide_to_long`), the mortality-table loader (`load_mortality`, SOA Pri-2012), and the sensitivity-sweep scaffolding (wage/savings/equity-allocation/immigration axes, vectorized NumPy). A Québec housing model would need a genuinely different Layer 1 (owner-cohort inventory by age/tenure, not equity savings/distribution) and would want StatsCan/CMHC housing-starts and resale data the current layer never wires — but the age-cohort-projection-with-sensitivity-band *method* and the Census/StatsCan population-pull pattern are directly transplantable as a starting shape, not as a library dependency.

**(4) Doctrine constraints — money-path coupling.**

The demographic-confidence layer is explicitly NOT money-path revenue substrate — the Y1 memo rules it a thesis-validity signal only, with "no capture fraction" language repeated three times. It informs VRP sizing doctrine (SINGULARITY.md compound window, tier-allocation zones) but is not itself a P&L-generating strategy. A housing model should inherit the same framing discipline the memo modeled: don't invent a fund-capturable dollar flow from a market-wide demographic pattern. There is no shared code library to couple into (research/ can't be imported into packages/), so there's no accidental money-path coupling risk from a shared-dependency standpoint — the risk is purely about the housing model similarly overclaiming financial/thesis relevance it doesn't have, if it's meant to feed fund decisions. **Open question to resolve before scoping the housing model:** is it meant to inform the fund (another sizing/tripwire input, same "informs, no capture fraction" discipline) or is it mission-side (North Star "land" vector, personal/mission housing-market intelligence unrelated to VRP)? That distinction determines whether it lives in mm-infra doctrine-adjacent territory at all, or is a fully separate standalone analysis.

**(5) Would it duplicate anything? No — overlaps on substrate and method, disjoint on everything else.**

Overlap: same class of input data (Census/StatsCan age-cohort population projections, immigration variants, mortality tables) and the same deterministic-projection-with-sensitivity-bands method. Reuse: pattern-level only (dead code, no library). Disjoint: purpose (equity fear-premium/VRP demand vs. residential housing supply-demand balance), asset class (US-listed equities vs. Québec real estate), geography (US+Canada broad vs. Québec-specific), mechanism (wealth-transfer-into-options-hedging vs. owner-sell/transfer-vs-immigrant-buyer flow), and output (VRP sizing doctrine vs. presumably a housing-market read). There is no computational or strategic duplication — a Québec housing model is a genuinely separate model that happens to share a demographic-projection ancestry, not a reimplementation of anything live or dead in mm-infra.
